Week 1 · Lab · Offline, no AWS calls

Pricing the support assistant

4,754 words · about 90 minutes of work

01What you do in this lab

In this lab, you work out what Support Assistant v1 costs to run. You use only the dated prices in data/pricing.json and the ledger code that you met on Day 2. The lab makes no AWS calls, so it costs nothing and you can do it before your AWS account is ready.

By the end of the lab, you can:

  • read the price register and say what each price applies to, and when the register needs checking again;
  • calculate the cost of one call from a Converse usage block, and check your result against model_cost() in ledger.py;
  • calculate the effect of prompt caching, the one-hour cache, long prompts and batch inference on the cost;
  • name two cases in which model_cost() reports less than Bedrock charges; and
  • forecast a month's cost of the assistant for several models, and write a short cost note for Kestrel.

02Before you start

You need the tools that the pre-work installs: uv and Python 3.12 or 3.13. You don't need AWS credentials.

  1. Unzip the Week 1 exercise package, week1-learner-lab.zip, that the instructor gave you. It creates the folder week1-lab.
  2. Open a terminal in week1-lab and create the environment, if you haven't already for another exercise.
  3. Change to the Exercise 2 version of the assistant. Its ledger.py is complete, and the lab imports it.
  4. Save the starter file below as cost_lab.py in that folder. It has two functions to complete, each marked with a TODO Task comment. You don't need to change anything below the line that says so.
  5. Run it.

Run the file again after each task. The first time, Task 1 prints the price register and the other tasks print Not done yet.

03Task 1: Read the price register

Open data/pricing.json in an editor, and run cost_lab.py. Task 1 prints each model's prices per million tokens and three ratios: output to input, cache read to input, and batch input to input.

Answer these questions from the file and the output. Write your answers down, because Task 5 uses them.

  1. When were the prices read, from which page, and for which Region and inference type?
    Show the answer
    On 31 October 2026, from the Amazon Bedrock pricing page, for Europe (London), eu-west-2, through the EU geographic cross-Region inference profiles. A cost calculated from the file is only as current as read_on. The file's last note asks for the prices and lifecycle stages to be checked again before each cohort.
  2. For every model, output costs five times as much as input. What does that mean for Kestrel?
    Show the answer
    An answer token costs five times as much as a question token, so the length of the answer matters more than the length of the question. A limit on output tokens, such as MAX_TOKENS = 700 in config.py, also limits the most that one call can cost.
  3. Which row has a cache-read ratio that differs from the others, and what does the register say about it?
    Show the answer
    Claude Sonnet 5.5. Its cache read is 0.11 USD per million tokens, 5% of its input price; for every other model it is 10%. A note in the register says this price was checked for the EU profile on 31 October 2026. A price that breaks the pattern is worth checking at the source, and recording that you have checked it, as the register does.
  4. Claude Sonnet 4.5 costs the same as Claude Sonnet 4.6. Why should Kestrel not choose it?
    Show the answer
    Its lifecycle stage is Legacy, with an end of life on 8 April 2027. Day 2's model-selection method removes a model that isn't Active before any test, whatever its price.
  5. The global profiles for the 5.5 models are about 10% cheaper. Can Kestrel use them to save money?
    Show the answer
    No. A global profile can route a call to any commercial Region. Kestrel's rule is that its data stays in Europe, which is why config.py uses the EU profile. The register lists the global prices for comparison only.

04Task 2: Price one call

Complete the first part of call_cost(). For now, price only the input and output tokens:

  • the inputTokens multiplied by the row's input price,
  • plus the outputTokens multiplied by the row's output price,
  • divided by one million, rounded to eight decimal places, with the status calculated.

Use usage.get("inputTokens", 0) rather than indexing, because a usage block can leave out a field. Run the file. Task 2 prices the Day 2 worked example, 25 input and 31 output tokens, on every model and compares your result with ledger.model_cost(). Every line must say same.

Check the first line by hand: (25 × 1.10 + 31 × 5.50) ÷ 1,000,000 = 0.000198 USD, the figure in the Day 2 handbook.

Common mistake Forgetting to divide by one million gives a cost a million times too high. The prices in the file are per million tokens, not per token.

05Task 3: Price caching, long prompts and batch

Finish call_cost() so that it prices every kind of call that the register covers. Work through the four parts in order and run the file after each one.

Part A: cache reads and writes

When caching applies, inputTokens counts only the input that wasn't read from or written to the cache. Add cacheReadInputTokens at the cache_read price and cacheWriteInputTokens at the cache_write_5m price.

Task 3a models 20 calls within five minutes that share a 5,000-token prefix, with 300 tokens of new input and 250 tokens of output in each. The first call writes the prefix to the cache and the other 19 read it. The prefix is longer than 4,096 tokens, the minimum that the Day 2 handbook gives for Claude Haiku 4.5, so Bedrock can cache it.

The cache saves about 64% across the 20 calls. But the call that writes the cache costs more than the same call without caching, because a five-minute write costs 1.375 USD per million tokens against 1.10 USD for plain input. Caching pays only when later calls read the prefix before it expires.

Part B: the one-hour cache

The course model also supports a one-hour cache, whose writes cost 2.20 USD per million tokens. When cache_ttl is "1h", price cache writes at cache_write_1h.

Part C: long prompts

The Claude Haiku 5.5 row has a long_context block. When the whole input, that is inputTokens plus the two cache fields, is more than 100,000 tokens, use the prices in that block for the whole call, and return the status calculated_long_context. The constant LONG_CONTEXT_THRESHOLD holds the limit. Other rows have long_context set to null, so they keep their normal prices.

Note The register records the rule from the Claude Haiku 5.5 model card as it stood on 31 October 2026. Check the model card before you rely on it for a real estimate.

Task 3b compares your function with model_cost() for parts B and C.

Part D: batch

When batch is true, price the input and output at batch_input and batch_output. If either price is null, as it is for both 5.5 models, return (None, "no_batch_price"). Caching works only with on-demand calls, so if a batch usage block has cache tokens, return (None, "cache_not_in_batch").

For the 4.x models, batch halves the price. Batch suits work that can wait, such as summarising every case in cases.json overnight, not a customer waiting for an answer.

What model_cost() gets wrong

Look at the two lines of Task 3b. In both, model_cost() reports less than Bedrock would charge:

  • It prices every cache write at the five-minute price. The usage block doesn't say which time to live the request asked for, so a client that uses the one-hour cache must pass that to the cost function. Here the ledger reports 0.008580 USD for a call that costs 0.012705 USD.
  • It ignores the long-context prices, so a 120,000-token prompt to Claude Haiku 5.5 is recorded at a fifth of its cost.

The course model uses neither, so the Week 1 ledger is correct for the exercises. Record both gaps in your evidence pack. A cost record that is wrong only for features you don't use yet becomes wrong without warning when you start using them.

06Task 4: Forecast a month

Complete monthly_forecast(). It forecasts a month of the assistant for one model, from the assumptions in ASSUMPTIONS. These figures are for the lab only, not Kestrel's measured traffic:

Questions a day1,500Kestrel serves about 180,000 homes and small businesses
Days in the month30
Model calls for each question3The Day 3 tool loop calls the model more than once for one answer
Retry rate5%Every retry is a new attempt that the ledger records, and a new charge if it succeeds
Usage of each call2,400 input and 300 output tokensThe system prompt, tool definitions, retrieved passages and history make the input much longer than the question

The function returns a dictionary with these keys:

KeyHow to calculate it
questionsQuestions a day × days
attemptsQuestions × calls for each question × (1 + retry rate), rounded to a whole number
model_usdAttempts × the cost of one call from call_cost(), rounded to two decimal places
retrieve_usdQuestions × Retrieve calls for each question × prices.retrieve_per_1000 ÷ 1,000, rounded to two decimal places
total_usdmodel_usd + retrieve_usd, rounded to two decimal places
per_question_usdtotal_usd ÷ questions, rounded to six decimal places

Answer these questions:

  1. By how much does the bill change if the course model is replaced by Claude Sonnet 4.6?
    Show the answer
    From 653.11 USD to 1,869.32 USD a month, nearly three times as much. Only an evaluation on Kestrel's own cases, as on Day 2, can show whether the larger model's answers are worth the difference.
  2. With Claude Haiku 5.5, what is the largest part of the bill?
    Show the answer
    Not the model. Its model cost is 60.81 USD, and the 45.00 USD of Retrieve calls becomes 43% of the total. When a model becomes cheap, check the other parts of the bill before you optimise further.
  3. Which costs does the forecast leave out?
    Show the answer
    Knowledge base storage at 5.00 USD per GB a month, which is small for the 25 Kestrel documents; agentic retrieval, at 4.00 USD per 1,000 calls plus the Retrieve calls it makes; AgentCore Gateway and CloudWatch charges when they are used; failed and interrupted attempts whose usage is unknown; and caching, which would lower the input cost if the shared prefix were long enough to cache.
  4. Change the retry rate in ASSUMPTIONS to 0.25. What happens, and what would you check in the ledger?
    Show the answer
    The attempts rise to 168,750 and the cost of the course model to 723.94 USD of model calls. A high retry rate usually points to throttling. Check the ledger's error_code and will_retry fields and the account's service quota for the course model before you plan for it.

Set the retry rate back to 0.05 when you have answered the last question.

07Task 5: Write a cost note for Kestrel

Write a note of no more than 200 words for Kestrel's head of support. It recommends a model for the assistant on cost, and it says how sure you are. Include:

  • the monthly forecast for the course model and for one alternative, and the date of the prices;
  • the assumptions that move the forecast most, and how Kestrel can measure them from the ledger once the assistant runs;
  • why the global profiles aren't an option, even though they cost less;
  • whether caching is worth testing, and what the test would need to show; and
  • the two gaps in model_cost() from Task 3, and when they would matter.

Save the note in your evidence pack. The instructor may ask about it at the Friday review.

Tip A forecast is only as good as its assumptions. Say which numbers are measured and which are estimated, and give a range rather than a single figure where you can.

08Review questions

  1. A Converse usage block reports 300 input tokens, 5,000 cache-read tokens and 250 output tokens. How many input tokens did the call process in all?
    Show the answer
    5,300. inputTokens counts only the input that wasn't read from or written to the cache, so the total input is the sum of the three input fields.
  2. Why does the ledger record the cost of a failed attempt as null and not as zero?
    Show the answer
    Because the client couldn't measure it. The model may have generated tokens that Kestrel will pay for. A null tells a reviewer that the total is incomplete; a zero would hide that.
  3. When does prompt caching cost more than not caching?
    Show the answer
    When a prefix is written to the cache and not read again before it expires. The write costs more than plain input, 1.375 USD against 1.10 USD per million tokens for the course model, so a single call with caching costs more.
  4. Why is batch inference not a way to lower the cost of the support assistant's answers?
    Show the answer
    A batch job returns its results later, not while a customer waits. It also doesn't support caching, and the 5.5 models have no batch price in the register. It suits work that can wait, such as summarising every case overnight.
  5. What must you do before you use these prices for a new cohort or a customer estimate?
    Show the answer
    Check each price and lifecycle stage on the Bedrock pricing page and the model cards, update read_on in the register, and say the date of the prices in every estimate.
